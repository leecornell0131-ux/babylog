## 구현한 것

1. **위젯 요약 D1 저장**: Worker DB 바인딩이 있으면 summaries 테이블에 가족별 최신 요약 1행. 토큰 목록은 KV 유지. 기존 KV의 s: 요약은 첫 조회/전송 때 읽어 D1에 옮기고, 삭제하지 않는다. DB 바인딩 없는 기존 배포는 이전 KV 경로 유지. DB 오류를 몰래 KV 쓰기로 우회하지 않는다. 그 경우 오류를 반환하며 원본 육아 기록은 별도 Firestore에 있다.
2. **동시성**: SQL upsert의 at 조건으로 늦게 온 요청이 최신 요약을 덮지 못하게 함. 같은 at은 재시도 가능. at은 여전히 클라이언트 시각이므로 폰 시계 오차 문제까지 해결한 것은 아님.
3. **웹 전송 큐**: 표시 필드가 동일하면 at만 달라진 저장은 생략. 날짜/이름/생일/진행 중 수면·수유 등 기존 필드는 모두 비교. 전송 실패를 완료 처리하지 않고 별도 localStorage `babylog-notify-v1`에 최신 요약 하나만 저장. 다음 저장/온라인/화면 복귀/서버 스냅샷 시 복구. 무한 타이머 재시도나 주기 조회 없음. 응답이 stale이면 해당 내용을 성공 비교값으로 기억하지 않음.
4. **상대/다른 탭 변경**: 서버 수신 내용이 달라지면 성공 비교값 무효화. 전송 대기 중이면 최신 합쳐진 화면 요약으로 교체. 자기 echo와 동일 내용은 무시해서 최적화가 무효화되지 않게 함.
5. **배치 묶음**: sync.js에서 한 저장을 400개씩 여러 Firestore 배치로 나누더라도 모두 성공한 뒤 notify 예약 1회. 부분 실패 상태는 알리지 않음. 원본 기록 업로드 자체는 기존 방식.
6. **FCM 오류**: 일시 실패를 HTTP 503으로 반환하여 새 웹 큐가 실패를 기억하게 함. 동일 at 재전송 가능. 구버전 웹은 예전처럼 오류를 무시할 수 있고, 구버전 APK의 summary 복구 경로는 유지.
7. **브라우저 사전 확인**: OPTIONS에 Max-Age 추가. 브라우저별 캐시 한도가 있으므로 OPTIONS가 모두 사라지는 것은 아님.
8. **새 APK의 15분 조회 제거**: 초기화/onLocal에서 기존 Job ID 7101 취소. PollJob 클래스/manifest는 유지하되 실행돼도 즉시 종료. FCM, 로컬 위젯 갱신, 앱 실행 후 Firestore 수신→bridge→위젯 갱신은 유지. 원래 있던 poll() 메서드는 남아 있지만 새 예약/호출 경로는 없음.
9. **PWA 0.3.23**: sw.js와 index.html 버전 일치. web-notify.js도 오프라인 shell에 포함.
10. **배포 준비**: 테스트 성공→D1 준비/추가형 SQL migration→Worker 배포 순서. main에서만 실서버 workflow 동작. D1 준비 실패 시 Worker 배포 단계까지 가지 않음. 새로운 Cloudflare API 권한이 필요하면 기존 운영자 설정을 확인할 것. 사용자에게 비밀키를 채팅에 붙이도록 요청하지 말 것.

## 구버전 갤럭시 혼용

**기존 API URL/요약 응답/FCM 데이터 필드, babylog-v1, BabyApp, BabySync.local, end:null, Firestore ID/u/del 모두 유지했으므로 혼용을 전제로 구현했다.** 혼용 실기기 검증은 아직 하지 않았다.

구버전 APK는 계속 15분 조회하므로, 그 요청을 줄이려면 APK 업데이트가 필요하다. 서버가 204를 반환해도 들어오는 요청은 줄지 않는다. 구버전의 /summary API를 폐쇄하면 안 된다. 위젯의 로컬 1분 시계 갱신은 서버 조회가 아니므로 유지했다.

## 사용자의 오늘/내일 비교 요청

구조적으로 가능하다. **같은 가족 코드와 같은 기록을 유지하고 전송 방식만 바꾸는 비교**다. 비교용으로 새 가족을 만들거나 Firestore를 초기화하지 말 것. 날짜만 바뀐다고 자동 적용되지는 않는다. 스케줄 배포/자동화는 만들지 않았다.

### 권장 3단계

| 단계 | 아이폰 웹 | 갤럭시 | 서버 | 확인할 효과 |
|---|---|---|---|---|
| A: 오늘 기준 | 기존 | 기존 APK | 기존 KV | 기준 사용량 기록 |
| B: 개선 웹/서버 | 0.3.23 | 기존 APK 유지 | D1 | KV 요약 쓰기 감소, 의미 동일 요청 생략. 15분 조회는 남음 |
| C: APK까지 전환 | 개선 웹 | 검증된 새 APK | D1 | 갤럭시 정기 조회 제거 효과 추가 |

B가 안정적인지 확인한 뒤 C로 간다. 처음부터 전부 바꾸면 어느 변경의 효과/문제인지 구분하기 어렵다. 이 PR을 통째로 main에 합치면 웹/서버/최신 APK 릴리스 자동화가 함께 움직일 수 있으므로, **실제 전환 때는 서버·웹을 먼저 적용하고 APK 배포는 별도 PR/수동 단계로 분리하는 것이 권장**이다. 현재는 구현을 리뷰할 한 브랜치에 모아둔 상태다.

### 매일 비교할 값

같은 시간대 24시간, 가능하면 2–3일씩 비교. Cloudflare/Firebase 대시보드 집계 시간대를 맞추고 개발 테스트 시간은 별도 표시. 원본 기록 내용을 서버 로그에 새로 수집하지 않는다.

| 항목 | A 기준 | B 웹/서버 개선 | C APK 개선 |
|---|---|---|---|
| 관찰 시작/종료 시각·시간대 | 기입 | 기입 | 기입 |
| 실제 저장 동작 수(시작/끝/수정/삭제 각각) | 기입 | 기입 | 기입 |
| 앱 새 실행/복귀 횟수 | 기입 | 기입 | 기입 |
| Worker 전체 요청 / notify / summary / OPTIONS | 기입 | 기입 | 기입 |
| KV 읽기 / 쓰기 | 기입 | 기입 | 기입 |
| D1 읽은 행 / 쓴 행 | 없음 | 기입 | 기입 |
| Firestore 읽기 / 쓰기 | 기입 | 기입 | 기입 |
| 위젯 누락/지연·앱 복귀 후 복구 여부 | 기입 | 기입 | 기입 |

하루 총량만 비교하지 말고 **notify 요청÷저장 동작 수**, **KV 쓰기÷저장 동작 수**도 비교한다. 수면 시작과 끝은 저장 2번이다. D1 개선의 주효과는 저장소 병목 완화라 Workers 요청 수 자체가 크게 줄지 않을 수 있다. 1회 요청을 저장 1회로 오해하지 말 것. 초기 migration/최초 앱 갱신/처음 참여/브랜치 빌드 테스트 소비는 별도다.

이전 보고서의 약 130가구/260명은 가구당 저장 50회·Firestore 읽기 약 300회/일 가정의 여유 있는 계획값이다. 이번 작업에서 실측한 수용량이 아니다. Firestore read 최적화/최근 이틀 쿼리/영구 캐시 변경은 하지 않았으므로 수천 가구를 보장하지 않는다.

## 실제 전환 전에 남은 일

1. 이 브랜치 diff/Actions를 검토하고 서버·웹과 APK 배포를 분리. 기존 운영 환경의 무료 플랜/토큰 D1 권한 확인.
2. 실서비스와 별도의 테스트 Worker/D1/가짜 가족 데이터로 원격 바인딩과 FCM 테스트. 테스트 서버 주소/가족 코드를 운영 사용자의 설정에 덮어쓰지 말 것.
3. 사용자 기기에서 백업 파일을 보존하고, 관찰 시작값 기록. 로컬 저장소/가족코드를 초기화하지 않는다.
4. 서버 URL을 바꾸지 않고 D1을 먼저 준비한 뒤 Worker 전환. / 건강 확인의 summaryStorage=d1과 가짜 테스트 가족의 summary 경로를 확인. 유료 업그레이드나 카드 등록은 하지 않는다.
5. 아이폰 웹 0.3.23에서 수유 생성/수정/기저귀/수면 시작·종료/삭제/오프라인 복귀를 확인하고 기존 갤럭시 위젯이 받는지 확인. 테스트 기록은 명확히 구분하고 기존 기록을 건드리지 않는다.
6. 이상 없을 때 사용량 관찰. 앱 삭제·재설치·초대코드 재발급 없이 진행한다.
7. APK 빌드만으로 FCM 전달성을 보장할 수 없다. 15분 복구를 제거하면 푸시 누락 시 다음 앱 실행 전까지 위젯이 늦을 수 있으므로 **새 APK 일반 배포 전에 절전/잠금 실기기 확인**이 필요하다. 마지막 동기화 시각/새로고침 UI는 이번 변경에 추가하지 않았으며 후속 UX 작업이다.

## 복구 지침

현재는 미배포라 main을 그대로 쓰면 된다. 복구 태그는 소스 기준점이고, 사용자 기록 백업을 대신하지 않는다.

전환 후에는 구성별로 복구해야 한다:

- 웹 문제: web/sync/sw를 이전 코드로 되돌리되 SW 버전을 **새 번호**로 올려 재배포. D1 서버를 그대로 두어도 기존 웹/구버전 APK API와 호환된다. 기록/가족코드는 삭제하지 않는다.
- APK 문제: 설치된 폰의 APK는 Git revert만으로 돌아가지 않는다. 기존 소스를 **더 높은 versionCode, 같은 서명 키**로 다시 빌드해야 덮어 설치할 수 있다. 앱 삭제는 로컬 자료 손실 위험 때문에 하지 않는다.
- Worker 문제: D1 전환 이후의 최신 요약은 옛 KV에 자동 복제하지 않는다(복제하면 KV 한도 개선을 잃음). 따라서 **이전 Worker를 무작정 롤백하면 옛 위젯 요약이 보일 수 있다.** D1 바인딩을 유지하는 수정 배포를 우선하거나, 최신 요약을 KV에 명시적으로 재이관한 뒤 옛 Worker로 되돌린다. 대량 재이관은 KV 하루 1,000회 한도도 고려한다. 원본 Firestore 기록은 이 요약 복구와 별개다.

무중단은 테스트/점진 적용 목표이지, 외부 Firebase/Cloudflare/FCM 장애까지 100% 보장하는 주장은 아니다. 다음 담당자는 위 남은 실기기/원격 검증을 완료하기 전 '실서비스 개선 완료'라고 사용자에게 말하지 말 것.
