# 서버 사용량 검토 및 Claude 인계 기록

작성: Codex, 2026-10-20. **분석 및 문서화만 수행. 앱 코드 수정·서버 배포·요금제 변경 없음.**

## 기준과 현재 상태

- 최초 분석 main: `efdd7a9ee919dd80931c9b284a0707ff5409d222`.
- 문서 작성 직전 main: `48e3a874e4514e92b397e1fe5c617373b7902b82`. 두 커밋의 차이는 iOS 앱 틀/빌드 설정 추가이며, 이번에 검토한 sync.js, push-server/, firestore.rules, Android 코드는 동일함.
- 별도 체크아웃에서 분석했으며 기존 개발 폴더/다른 에이전트 작업을 수정하지 않음.
- 이 문서의 개선안은 **제안**이며 미구현. 실제 서비스의 Firebase/Cloudflare 대시보드 수치, 실기기 동작, 부하/청구 검증은 하지 않음.
- 사용자의 7시간 97요청은 개발 테스트 포함 관측값. 경로별 로그가 없어 그 97회를 기능별로 역산할 수 없음.

## 변경하면 안 되는 계약

운영비 0원 지향: Firebase Spark/카드 미등록/Cloud Functions 없음, Workers Free 유지. 사용자에게 Firebase 설정을 맡기지 않음.

다음 이름과 저장 형식을 유지: localStorage `babylog-v1`, `window.BabyApp`, `window.BabySync.local`, 진행 중 기록 `end:null`. 기존 events의 ID, 수정 시각 `u`, 삭제 표식 `del`도 구버전과 함께 읽고 쓸 수 있어야 함. 아내의 구버전 Android APK가 당분간 남는다는 전제로 판단할 것.

## 1. 현재 언제 무엇을 호출하는가

| 동작 | Firestore | Workers 및 KV |
|---|---|---|
| 공유 미사용 상태에서 열기/기록 | 가족 리스너 0, 기록 쓰기 0 | 일반 기록에 따른 notify 없음. Firebase/FCM SDK 초기화 등의 통신까지 모두 없다는 의미는 아님 |
| 공유 중 앱 새로 열기 | events와 가족 설정 문서에 리스너 2개. 바뀐 로컬 데이터가 없다면 쓰기 0 | 웹 시작 자체는 notify하지 않음. Android는 필요시 토큰 등록; 동일 가족/토큰이면 보통 생략 |
| 기록 1개 생성/수정 | 보통 문서 쓰기 1. 두 사람의 리스너에 전달될 때 읽기도 발생 | 커밋 성공 후 notify 예약. 정상 1배치 저장이면 POST /notify 1회. 브라우저 OPTIONS가 추가될 수 있음 |
| 수면 시작 후 종료 | 시작과 종료가 각각 저장되면 총 쓰기 2 | 일반적으로 notify도 각각 발생 |
| 여러 기록 변경 | 변경된 문서 수만큼 쓰기. 400개씩 배치하지만 배치 전체가 쓰기 1회인 것은 아님 | 배치 성공마다 notify 예약. 1.5초 debounce가 합칠 수 있으나 여러 배치가 느리게 끝나면 복수 요청 가능 |
| 기록 삭제 | 실제 삭제 대신 해당 문서에 del:true 쓰기 | 저장 성공 후 notify 경로 |
| 아이/기록 항목/누락 설정 변경 | 변경 시 가족 설정 문서 쓰기 | 커밋 후 notify. 위젯 표시가 같아도 요청할 수 있음 |
| 화면 렌더/매분 화면 갱신/상대 기록 수신 | 이것만으로 새 쓰기 없음. 상대 기록 수신은 리스너 읽기 | 이것만으로 notify 없음 |
| 브라우저 새로고침 | JS와 리스너 재시작. 로컬 동기화 커서는 유지 | 변경이 없다면 시작만으로 notify하지 않음 |
| 공유 생성 | 가족 문서 1 + 멤버 문서 1 + 기존 로컬 기록 업로드 | 초기 업로드에 따른 notify 가능 |
| 초대코드 참여 | 멤버 쓰기 1 + 가족 문서 get + 리스너 초기 수신. 첫 동기화는 과거 기록도 필요 | 보유 로컬 기록 업로드가 있으면 notify 가능 |
| Android 백그라운드 작업 | 직접 Firestore 읽지 않음 | **15분 주기 GET /summary**. 설정상 하루 96회/기기; 실제 실행은 절전·네트워크·재시도에 따라 달라짐 |
| FCM 알림 수신 | 직접 Firestore 재조회하지 않음 | 받은 요약을 위젯/알림에 적용. 수신 자체가 재알림을 만들지는 않음 |

### 전체 기록을 매번 받는가?

**현재도 단순 전체 다운로드가 아니라 수정 시각 기반 증분 동기화다.** sync.js:105–110은 저장된 cursor에서 5분을 뺀 시점보다 `u`가 큰 문서를 듣는다. 과거 날짜의 수유 기록도 오늘 수정하면 u가 갱신되어 수신된다. 첫 참여/커서 초기화 때는 전체 내역을 받을 수 있다.

다만 리스너를 만들 때 쿼리의 하한이 고정된다. 앱을 오래 켜두면 이후 커서가 전진해도 기존 쿼리 범위는 줄지 않는다. Firestore 영구 디스크 캐시는 설정되어 있지 않다. 따라서 재접속/재시작 때 재조회 읽기가 생길 수 있다. 앱의 localStorage에 기록이 있다는 것과 Firestore가 영구 캐시를 사용하는 것은 다른 문제다.

리스너 콜백 안에서 pending/removed 항목을 무시하는 코드는 이미 받은 문서의 과금까지 취소하지 않는다. 가족 권한을 확인하는 rules의 exists()도 별도 읽기를 발생시킬 수 있다. 보안을 풀어서 절약하지 말 것.

### Workers 호출별 저장 비용

| 경로 | 들어오는 요청 | KV 읽기 | KV 쓰기 |
|---|---:|---:|---:|
| OPTIONS 사전 확인 | 1 | 0 | 0 |
| GET /summary | 1 | 1 | 0 |
| POST /notify 정상 처리 | 1 | 2 | **1** |
| POST /notify 오래된 at 거절 | 1 | 1 | 0 |
| POST /register | 1 | 1 | 새 토큰이면 1, 같으면 0 |
| POST /unregister | 1 | 1 | 해당 토큰이 있었으면 1 |
| GET / 상태 확인 | 1 | 0 | 0 |

notify는 **받을 기기가 0대여도 요약을 먼저 KV에 쓰며**, 요약 내용이 같거나 at이 같아도 다시 쓴다. 만료 토큰 정리에는 추가 KV 읽기/쓰기가 생길 수 있다. FCM/OAuth 외부 호출은 별도 subrequest로 보며, 위 표의 앱→Worker 요청과 섞어 세지 않았다.

web-notify의 설정 파일 fetch 및 Android refreshConfig는 GitHub 파일 요청이지 Worker 요청이 아니다. index.html의 sw.js 업데이트 확인도 이 Worker 사용량이 아니다.

## 2. 가장 큰 병목

공식 무료 한도: Workers 요청 100,000/일, **Workers KV 쓰기 1,000/일**, KV 읽기 100,000/일. Firestore 읽기 50,000/일, 쓰기 20,000/일. 모두 전체 사용자 합산이다.

가족당 notify 50회/일이면 KV 쓰기만으로 `1,000 / 50 = 20가구`가 한도다. 토큰 등록/정리가 추가되므로 실제 여유는 더 작다. 사용자가 계산한 330–400가구는 Workers 요청 한도만 나눈 값이며 현재 구조 전체의 수용량은 아니다.

현재 KV는 같은 키에 초당 쓰기 제한도 있어 동시 저장/여러 배치가 몰리는 상황도 검증해야 한다. 요청 횟수, KV 쓰기, Firestore 읽기를 각각 분리해서 보자.

## 3. 효과 순 개선 제안 및 구버전 호환

### A. 위젯 최신 요약의 잦은 저장을 KV에서 분리

KV 쓰기 병목을 먼저 풀어야 한다. 무료 D1에 가족별 최신 위젯 요약 1행만 저장하고 드문 토큰 등록은 당분간 KV에 남기는 방식이 후보다. D1 Free는 읽은 행 500만/일, 쓴 행 10만/일, 총 저장소 5GB. 인덱스 변경도 쓴 행에 포함될 수 있다. 새 유료 결제를 요구하는 설계가 아니라 무료 관리형 저장소를 추가하는 제안이다. 쿼리/인덱스별 실제 행 사용량을 검증해야 하며 무료 무제한은 아니다.

기존 /notify, /summary, /register, /unregister URL과 응답 JSON, FCM 필드를 그대로 유지한다. 기존 KV 요약을 이관하거나 D1 미존재 시 KV를 읽는 전환 단계를 두고, 기존 at 비교 동작을 유지하면서 오래된 요청이 최신 행을 덮지 못하게 조건부 upsert를 구현한다. 클라이언트 시계 오차 문제는 별도 검토 대상이다. 기존 KV 내용을 먼저 지우면 안 된다.

**호환: 기존 API 계약을 유지하고 이관하면 구버전 Android APK도 업데이트 없이 사용 가능. Firestore 기록 형식 변경 없음.** 토큰을 KV에 남기면 신규 설치가 몰리는 날의 KV 등록 쓰기 한도는 남는다.

### B. 위젯 내용이 실제 바뀔 때만 notify

Firestore 기록 저장은 정상 유지하되, 위젯 요약이 같은 메모 수정 등은 알림을 생략한다. 비교에서 매번 달라지는 `at=Date.now()`는 제외해야 한다. 이름/생일/날짜 전환/진행 중 수면의 시작 시각 등 표시 의미가 있는 필드는 비교에 포함한다. 가족별 마지막 성공 요약을 별도 저장하고, 실패했는데 전송 완료로 표시하지 않는다. 최초 등록 기기의 초기 요약도 보장한다.

한 번의 논리적 저장에서 여러 batch가 생기면 모든 필요한 커밋이 끝난 뒤 알림을 합치는 방안을 검토한다. 서버 중복 방지도 같은 키 경쟁을 고려해야 한다. 모든 수유/수면/기저귀 저장이 위젯을 바꾼다면 이 최적화의 절약 효과는 작다.

OPTIONS에는 Access-Control-Max-Age를 추가해 브라우저 사전 확인을 캐시할 수 있다. 절감량은 브라우저 정책에 따라 달라지며 모든 OPTIONS가 사라지는 것은 아니다.

**호환: 기존 요약 필드·기록 저장 방식·엔드포인트를 유지하면 구버전과 혼용 가능. 생략 대상은 위젯 내용이 동일한 요청뿐이어야 함.**

### C. 새 Android APK의 15분 조회 제거

Push.kt:118–130의 JobScheduler 정기 조회를 해제하고 FCM 수신 + 앱을 실제 열 때 필요한 복구에 의존한다. 이미 등록된 주기 job도 취소해야 한다. FCM이 지연/누락되면 다음 앱 실행 전까지 위젯 복구가 늦어질 수 있으므로 실기기에서 확인해야 한다. 무폴링으로 항상 즉시 갱신된다고 보장할 수는 없다.

**호환: 기록 형식 변경 없어 구버전과 공유 안전. 다만 구버전의 15분 요청은 APK 업데이트 전까지 남는다.** 웹 JS만 바꾸거나 서버가 204를 반환해도 이미 들어온 요청 1회는 없어지지 않는다. 구버전을 위해 기존 summary API를 유지할 것.

### D. Firestore는 현재의 수정 시각 기반 동기화를 우선 개선

영구 디스크 캐시 적용과 중복 리스너/재연결 범위를 측정한다. 영구 캐시를 사용해도 30분 넘는 연결 해제 후 재연결 등은 새 쿼리 읽기로 계산될 수 있어 무료 재접속을 보장하지 않는다. 타이머 폴링은 추가하지 않는다.

최근 이틀만 듣는 별도 설계는 저장 일자보다 수정 시각 u를 기준으로 해야 한다. 마지막 커서 이후 누락분 전체를 먼저 따라잡고, 첫 기기/복구/오래된 기록 수정/삭제/오프라인 복귀/오래 진행 중인 end:null 기록을 모두 처리해야 한다. 항상 48시간 범위를 요청하면 기존 5분 겹침보다 오히려 많이 읽을 수도 있다.

**특히 S.events에서 이틀 이전 기록을 잘라내면 안 된다.** sync.js:79–80은 이전에 동기화한 ID가 로컬 events에서 없어지면 삭제로 판단한다. 단순히 오래된 기록을 배열에서 제거하면 상대 기기에서도 과거 기록이 삭제될 수 있다. 화면 표시만 최근 범위로 제한하고 전체 로컬 데이터는 유지하는 것이 먼저다.

**호환: 기존 events/ID/u/del/end:null과 전체 로컬 배열을 유지하는 캐시·리스너 개선은 혼용 가능. 별도 보관 형식/삭제 규칙 변경은 구버전 대응 설계 전까지 금지.**

### E. 공유 미사용 사용자

이미 fid가 없으면 sync.local 및 가족 리스너 경로는 서버 기록을 만들지 않는다. 공유를 켤 때 SDK를 지연 초기화하는 것은 부가 개선이며 현재 주된 비용 원인은 아니다.

**호환: 공개 함수와 저장소 이름을 유지하는 지연 초기화는 혼용 가능. 공유 전환/재가입 초기화가 빠지지 않게 확인해야 함.**

## 4. 하루 사용량 예시와 무료 가구 수

관측값이 아닌 **명시적 가정에 따른 정상 운영 예시**다. 가구별 실제 횟수를 대입해야 한다.

- 2명 공유, Android 1대 + PWA 1대.
- Firestore 기록 문서 쓰기 50회/일. 수면 시작·종료는 별도 저장. 최초 참여/대량 가져오기/설정 쓰기/재시도 제외.
- 두 기기가 모두 50개 변경을 구독. 하루 총 콜드 스타트 10회, 시작마다 평균 이벤트 2개와 가족 문서 1개 읽기.
- 기본 문서 읽기 약 `2×50 + 10×(2+1) = 130`. 권한 확인 읽기·재연결을 포함한 계획값은 **약 300/가구/일**로 둔다. 이 300은 실측값이 아니며 rules 평가/캐시/연결 상태에 따라 달라진다.
- 현재 notify 50회. 최적화 후 그중 20회가 위젯 내용 동일한 저장이라서 30회가 된다고 가정. 실제로 50회 모두 의미가 바뀌면 이 절감은 없다.
- OPTIONS는 POST당 최대 1회 붙는 보수적인 예시. Android 주기 조회는 명목 96회/일. 등록·실패·재시도·개발 테스트는 별도.

| 시나리오 | Workers 요청/가구/일 | KV 요약 쓰기/가구/일 | Firestore 읽기/쓰기 | 주요 한도상 가구 수 |
|---|---:|---:|---:|---:|
| 현재 예시 | 최대 196 = 96+50+50 | 50 | 약 300 / 50 | **20 이하: KV** |
| 알림 중복 절감, 구버전 APK 유지 | 최대 156 = 96+30+30 | 30 | 약 300 / 50 | **33 이하: KV** |
| 위 조건 + 모든 APK 주기 조회 제거 | 최대 60 = 30+30 | 30 | 약 300 / 50 | **33 이하: KV** |
| D1 요약 전환 + 알림 절감, 구버전 혼용 | 최대 156 | 0; 토큰 KV 쓰기는 별도 | 약 300 / 50 | **약 166: Firestore 읽기** |
| 위 조건 + 모든 APK 주기 조회 제거 | 최대 60 | 위와 같음 | 약 300 / 50 | **약 166: Firestore 읽기** |

가구 수 계산은 각 한도를 가족당 사용량으로 나눈 값 중 가장 작은 값이다. D1 전환 예시에서는 `min(100000/156, 50000/300, 20000/50, D1행 한도, 기타 한도)`로 본다. D1 요약 upsert가 30회면 최소 30행 쓰기이며 인덱스에 따라 더 많을 수 있다. KV를 계속 쓰는 토큰 등록 수용량도 별도 확인한다.

계획용 여유 20%를 두면 이 가정에서는 **약 130가구를 초기 운영 목표**로 잡는 편이 맞다. Firestore 실제 읽기가 200–350이라면 읽기 한도만 기준 약 142–250가구다. 영구 저장 용량/전송량/Worker CPU/FCM 전달성/대량 신규 가입/공유코드 악용까지 검증한 서비스 보장은 아니다. 사용자가 몇 년간 저장하면 Firestore 무료 1GiB 저장 한도도 별도 병목이다.

신규 기기가 기록 5,000개를 처음 받으면 기본 문서 읽기만 약 5,000회가 추가될 수 있다. 첫 동기화와 평상시 하루 소비량을 따로 집계해야 한다. 무료 요금제 유지 시 한도 초과는 무제한 무료 처리가 아니라 기능 실패/제한으로 이어질 수 있다.

## 5. 검증 기록과 다음 구현 순서

실서비스에 접근하지 않는 Node 모의 검증 14개 통과. 가짜 KV와 Firebase 함수를 주입한 코드 경로 검증이며 Firebase 청구 에뮬레이터/Android 실기기 검증은 아니다.

- notify 수신자 0명: KV 읽기 2, 쓰기 1 확인.
- 내용 동일/at 동일 요청도 KV 쓰기 1 확인.
- 오래된 at 요청은 쓰기 생략 확인.
- 동일 토큰 재등록은 쓰기 생략 확인.
- 동기화 상태가 일치하는 공유 시작: 리스너 2, 쓰기 0 확인.
- UI refresh 20번으로 커밋/notify 발생하지 않음 확인.
- 변경 기록 1개: 문서 쓰기 1, 성공 배치 notify 1 확인.
- 상대 기록 적용만으로 재업로드/재알림 없음 확인.
- 공유 없는 시작/로컬 저장: 리스너·쓰기·notify 0 확인.

재현 자료: 같은 폴더의 `usage-check.cjs`와 `usage-check-results.json`. 실행: Node 20 이상에서 `node docs/usage-check.cjs`. Firebase/Cloudflare 계정이나 네트워크 없이 동작하며 실서비스 데이터는 쓰지 않는다. 결과는 표준 출력으로 나오며 기존 JSON 파일을 자동 갱신하지 않는다.

다음 담당자 권장 순서:

1. 배포/개발 테스트와 평상시 사용을 나눠 24시간 경로별 요청, OPTIONS, KV read/write, Firestore read/write를 실측. 로그를 남기느라 KV 쓰기를 추가하지 말 것. 아이 기록/초대코드/토큰을 로그에 남기지 말 것.
2. 별도 구현 브랜치에서 D1 요약 전환 및 호환 이관 검증. 문서 작업 브랜치를 구현 완료로 오인하지 말 것.
3. 의미 있는 요약 비교/성공 후 전송 상태/한 저장의 batch 알림 합치기/OPTIONS 캐시 적용.
4. 구버전 APK와 신버전 웹, 신버전 APK를 섞어 생성·수정·삭제·수면 시작/종료·오프라인 복귀·첫 참여 검증.
5. APK 정기 job 취소와 FCM 지연 시 복구 검증. 구버전 트래픽은 따로 계측.
6. Firestore 캐시/연결 개선 전후 읽기 비교. 최근 이틀 제약은 별도 설계·검증 후 판단.
