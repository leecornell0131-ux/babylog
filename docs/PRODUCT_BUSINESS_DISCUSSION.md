# 제품·동기화·수익 구조 논의 (2026-10-20)

이 문서는 사용자와 Codex의 대화 요약이다. 축어록이 아니며, **사용자가 확인한 요구와 Codex의 제안·가정을 구분**한다. Claude도 같은 고민을 이어서 검토할 수 있도록 Git에 남겨 달라는 사용자 요청으로 작성했다. 코드 변경·유료 전환·광고 도입·배포 승인을 의미하지 않는다.

## 1. 사용자가 확인한 제품 요구

- **“외부에서도 공유되고 위젯도 자동 갱신된다”는 컨셉을 유지한다.** 배우자 한 명은 직장 등 외부에 있으므로 같은 와이파이에서만 동기화하는 방식은 요구에 맞지 않는다.
- 앱을 열 때만 동기화하면 홈 화면 위젯에 오래된 내용이 남을 수 있다. 비용을 아끼려고 핵심 사용 경험을 약화시키는 방향은 원하지 않는다.
- 사용자 표현: “애매하게 구현하는것보다 확실하게 쓰는게 맞지.”
- 자동 갱신을 목표로 하되, OS 절전·네트워크·푸시 지연까지 포함한 절대적 즉시성을 보장했다고 해석하지 않는다. 마지막 수신 시각과 실패 복구 등 신뢰성 설계가 필요하다.

## 2. 사용자가 제기한 사업 관점

- 사용자는 기존에 삐요로그 무료 플랜을 사용했다. 광고가 크게 불편하지 않았고, 떨어져 있는 부부 사이 동기화도 제공됐다.
- 두 사람이 비슷한 시점에 입력하면 잠깐 잘못 보이는 경험이 있었고, 기다린 뒤 기록을 삭제·재입력해 해결했다. 이는 사용자 경험 보고이며 원인을 분석한 결과는 아니다. 우리 앱이 같은 문제를 허용해도 된다는 뜻도 아니다.
- 무료 앱도 광고 등으로 운영·수익화할 수 있으므로, 우리 앱도 경제적인 운영 방법을 찾아야 한다는 문제의식이다.
- 질문: **“내가 월에 10만원이라도 벌려면 어떤 구조를 가져야하지?”**
- Codex는 이를 운영비 차감 후 월 10만원 목표로 해석했다. 세후 이익인지, 개발 인건비까지 포함하는지 사용자가 별도로 확정한 것은 아니다.

## 3. 동기화 구조에 관한 현재 이해

- 현재 기본 역할: 휴대폰 로컬 저장 → Firestore 기록 공유 → Cloudflare Worker의 위젯 요약·푸시 발송 처리 → FCM의 Android 푸시 전달.
- Cloudflare는 필수가 아니다. Firebase 중심 통합, Cloudflare 중심 통합, 별도 서버 등으로 역할을 대체할 수 있다. 대체 시 인증·접근 제어·충돌 처리·증분 동기화·푸시·복구 비용을 함께 비교해야 한다.
- 완전 P2P는 상대가 꺼져 있거나 오프라인일 때 전달 대기가 어렵고, 인터넷 연결 주선/중계와 모바일 백그라운드 제약도 남는다. 이 제품의 기본 운영안으로 합의한 적은 없다.
- 서버를 없애는 것보다 **가구당 비용을 줄이면서 외부 공유와 자동 위젯 갱신을 유지**하는 쪽으로 논의를 이어갔다.
- 경과 시간·통계는 기기에서 계산하고, 기록 변경분과 작은 위젯 요약만 전달하는 방향을 제안했다. 일부는 기존 구현에도 있다.
- “약 20가구”는 이전 KV 요약 쓰기 방식에서 특정 일일 사용량을 가정한 병목 계산이다. 제품의 경제적 한계나 개선 후 수용량이 아니다.

실제 구현/검증 상태는 [CLAUDE_SYNC_HANDOFF.md](CLAUDE_SYNC_HANDOFF.md), 이전 기준 분석은 [SERVER_USAGE_AUDIT.md](SERVER_USAGE_AUDIT.md)를 우선 확인한다. 기존 인계 문서상 개선 브랜치는 미배포이며, 이 대화에서는 원격 배포 상태를 새로 검증하지 않았다.

## 4. Codex가 제안한 수익 모델 — 미확정

**기본 무료 + 부담 적은 광고 + 가족 단위 유료 옵션**을 제안했다. 사용자는 아직 이 구성·가격·유료 기능에 동의하거나 구현을 요청하지 않았다.

| 구분 | 제안 내용 |
|---|---|
| 무료 | 기본 기록, 배우자 외부 공유, 위젯 자동 갱신, 기본 통계·백업·내보내기 |
| 유료 후보 | 가족당 월 2,900원, 한 명 결제 시 가족 공동 혜택 |
| 유료 기능 후보 | 광고 제거, 세밀한 패턴 비교·맞춤 통계, 추가 위젯 디자인/표시 항목, 꾸민 보고서 |
| 광고 후보 | 기록을 막는 전면 광고를 피하고, 무료 사용자 운영비를 보조 |

가장 큰 미검증 가정은 **무료 삐요로그 대신 우리 앱을 계속 쓰고 유료 기능에도 결제할 이유가 있는가**다. 위젯·음성 기록 등의 차별점은 실제 사용자 반응으로 검증해야 한다. 위젯만 사용하면 앱 내 광고 노출이 적을 수 있으므로 광고 수익을 과대평가하지 않는다.

## 5. 대화에 사용한 계산 — 예측이나 실측이 아님

### 구독 예시

가족당 월 2,900원, 수수료 15%, 월 운영비 30,000원을 가정했다. 아래 결과는 **부가세·소득세 등 세금, 환불, 개발 인건비, 유료 사용자 유치비를 제외한 단순 계산**이며 실제 정산액이 아니다. 운영비 3만원으로 해당 사용자를 감당한다는 검증도 없다.

`월 잔액 = 유료 가족 수 × 2,900원 × 0.85 − 30,000원`

| 유료 가족 | 월 결제 총액 | 위 가정에 따른 잔액 |
|---:|---:|---:|
| 30 | 87,000원 | 43,950원 |
| 60 | 174,000원 | 117,900원 |
| 70 | 203,000원 | 142,550원 |

Codex는 여유를 둔 후보 목표로 유료 70가족을 제안했다. 전환율을 가정상 3~5%로 놓으면 월간 활성 가족 약 1,400~2,334가족이 필요하다. 마지막 답변에서는 이를 약 1,500~2,500가족으로 반올림해 설명했다. 전환율은 업계 검증값이나 앱 실측값이 아니다. 육아 기록 집중 사용 기간이 끝나는 가족의 이탈과 신규 유입도 별도로 계산해야 한다.

### 광고 예시

월 광고 매출 130,000원에서 운영비 30,000원을 빼는 가정. 30일, 일간 활성 사용자 1명당 실제 광고 노출 5회를 가정했다. 가족 수가 아닌 **광고를 보는 사용자 수**다.

`필요 DAU = 130,000 ÷ (30 × 5 × eCPM ÷ 1,000)`

| 가정 eCPM (1,000회 노출당 수익) | 필요 일간 활성 사용자 |
|---:|---:|
| 500원 | 약 1,734명 |
| 1,000원 | 약 867명 |
| 2,000원 | 약 434명 |

단가와 노출 횟수는 계산용 가정이다. 실제 배너 수익·광고 채움률·지역·OS·동의 상태·앱 실행 빈도를 측정해야 한다. 앱 출시/개발자 계정 등 비용도 빠짐없이 반영해야 한다.

## 6. Claude와 함께 검토할 질문

1. 무료 삐요로그 대비 선택 이유는 무엇인가? 실제 보호자가 계속 사용할 차별점과 유료 결제 이유를 구분할 것.
2. 광고 중심/구독 중심/혼합 중 월 10만원 목표에 맞는 모델은 무엇인가? 월 2,900원은 후보일 뿐이며 연간·일회성 상품도 비교 가능하다.
3. 현재 구조 개선과 Firebase/Cloudflare 중심 통합의 운영비·개발비·안정성 차이는? 단순 서비스 개수로 평가하지 말 것.
4. 100·1,000·10,000 활성 가족별 월 비용은? 기록 쓰기, 초기/재접속 읽기, 저장 증가, 위젯 요약, 푸시, 복구 요청, 인증, 로그를 분리할 것. 무료 사용자 비용도 포함할 것.
5. 잠금·절전·통신 복구·동시 입력·구버전 APK 혼용에서 위젯 최신성과 기록 무손실을 어떻게 검증할 것인가? 주기 조회 제거에 따른 복구 약화를 함께 평가할 것.
6. 신뢰성 UX: 마지막 갱신 시각, 오래된 정보 표시, 수동 복구, 중복·삭제·충돌 처리에 필요한 것은?
7. 사용자 획득비 없이 목표 활성 가족을 모을 경로와 육아 단계 종료에 따른 이탈을 보충할 방법은?

먼저 검토와 계산을 이어가고, 결제·광고 SDK 추가, 요금제 변경, 전체 동기화 재작성, 실제 배포를 이번 문서 요청으로 승인받았다고 해석하지 않는다. 기존 실사용 기록과 구버전 호환을 보존한다.
